# Stage 0 - Pre-flight (no changes)

Nothing is written in the repo in this stage, and nothing in the state dir except the freshness lines of `project.md` (check 9); otherwise it only reports. Run it at the start of every `/deliver-ticket <ticket>` (new, resume, rework). Gate: none, unless a check fails.

## Checks (report each as ok / warn / FAIL, one line)
Each command below is its own Bash call (SKILL.md section 3c, "One script per Bash call"): never join two checks into one call.
1. **Claude Code version**: `claude --version` (alone in its call) >= 2.1.311 (the minimum tested; the review discussion resumes a subagent with `SendMessage`). Below -> warn; the review then uses a new reviewer per round (`5-review.md`).
1b. **Code Mode**: `printenv CLAUDE_CODE_EXPERIMENTAL_CODE_MODE` (its own call; exit 1 = unset). Set to anything other than empty or `0` -> **FAIL and stop**: "Code Mode (experimental) is not supported by deliver-ticket - quit, unset CLAUDE_CODE_EXPERIMENTAL_CODE_MODE (shell and the env block of ~/.claude/settings.json) or set it to 0, then start a new session". Not soft mode: no rule or hook of the skill was probed under Code Mode (the hooks also block the skill's scripts while it is on, and deny Code Mode's `REPL` tool).
2. **Init found**: project key (SKILL.md section 3), then `<state>/guard.json` (`<state>` = `<state root>/<project-key>`, SKILL.md section 3). Missing -> FAIL, but offer the way forward (SKILL.md section 1): "Project not initialised - run init now, then continue with ticket <ID>?" On yes the ticket input is saved with `<skill dir>/scripts/pending-ticket.sh save`, init runs in full, then this stage runs again from check 1 and the saved input is read with `take`; on no, stop. Run `<skill dir>/scripts/validate-guard.py <guard.json>` (its own call); exit not 0 -> FAIL, show its lines, stop. Then, as the next call, `<skill dir>/scripts/guard-write.sh verify --repo <repo_root>` (compares the file's sha256 with the last one `guard-write.sh` logged in `delivery.log`): exit 0 ok; exit 1 -> **FAIL**: `guard.json` was changed another way (the hooks block that), show the line and stop until I decide; exit 3 -> warn: no write recorded - expected for a `guard.json` that v0.1 init (on `main`) wrote, until it is adopted with an identical candidate through `guard-apply.sh` (my yes, init.md step 3).
3. **Config vs guard.json**: `config.md` or `config.local.md` newer than `guard.json` -> warn and offer to regenerate (init, re-run mode). `soft_mode: on` in config with `local` everywhere in `guard.json` stop points is expected, not drift.
4. **`<ASK>` left in config**: list the ones this ticket will need (verify commands, real-run tool, env files, regression scope, two test identities if a per-user server API or store is mapped in Risk). The stage that needs one stops and asks; never guess.
5. **Hook self-test, part A** (`init.md` step 4): first print exactly one line, `Next 2 calls are expected to be blocked (hook self-test): echo DELIVER_TICKET_SELFTEST, then a Write to ~/.claude/.deliver-ticket-selftest.`; then a Bash call `echo DELIVER_TICKET_SELFTEST` must be blocked, and a Write of `~/.claude/.deliver-ticket-selftest` must be blocked (afterwards print `Self-test A: both blocked, as expected`). Then `<skill dir>/scripts/install-hooks.sh status` (exit 0 = registered) and `<skill dir>/scripts/install-hooks.sh project-status --repo <main checkout>` (the project-level `WorktreeCreate` hook; not registered = worktrees are made by Claude Code, tell me, stage 1b then sets up env links and ports itself). Either part failing -> **soft mode** (SKILL.md section 5): tell me, record `mode: soft` in the ticket file at stage 1. If only the first call is not blocked right after install, ask me to start a new session and test there.
6. **Git**: inside a git repo; note whether this session is in the main checkout or in a ticket worktree. Uncommitted changes in the current directory -> warn (list `git status --short`, do not touch them).
7. **Parallel limit**: count `tickets/*.md` in the project state whose `state:` is `active` and that have a `worktree:`. More than `max_parallel.tier_bc` (tier B/C) or `max_parallel.total` (from `guard.json`) -> warn; I decide. Never refuse.
8. **CLAUDE.md** and `.claude/rules/` of the repo: read them now (they win over config, and the risk paths in them are always in the mapping). Report any conflict with config.
9. **Project knowledge freshness** (skip if `<state>/project.md` does not exist - the project was initialised before it existed; say so and offer an init re-run): `<skill dir>/scripts/project-map-stale.sh apply <state>/project.md --guard <state>/guard.json`. It uses git on the base branch as the clock - the local ref `guard.json` `base_branch`, the same ref stage 1b creates worktrees from; stage 0 does not fetch - only added / deleted / renamed files under a section's watch globs, or a changed manifest / lockfile / framework config, make a section stale; modified files do not. Sections with no structural change get `checked:` advanced to the base HEAD (no rescan); stale ones are marked `stale: yes (reason)` and **not** rescanned here. Report the stale sections. A `propose-init` line (a workspace config file changed, the lockfile type changed = package-manager switch, or a new top-level app/package directory) -> propose an init re-run (full refresh of `project.md`); I decide. A dependency added, a modified lockfile: nothing. A changed `scripts` block in a `package.json` under a section's watch globs: that section (usually Commands) is marked stale, nothing else. The rules come from the `dt:` lines of `profiles/*.md`. Read-only alternative: `check` instead of `apply`.
10. **Session bound** (ticket calls only; skip for `init`) - the fail-closed point of the binding: `<skill dir>/scripts/session-map.sh show <ID> --session <session id> --repo <repo_root>`. Exit 0 = the bind hook fired and the full guard applies to this session. Exit 1 / error = **FAIL and stop** (if this conversation holds a context line `this session is still bound to ticket X in project Y ...`, that is why: the session has an open ticket in another project and was deliberately not re-bound - say so and ask me to close or pause X, or to start a new session; do not bind by hand over it): this session is not bound, so the main-checkout guard is off for it and the ticket would run unguarded (the hook is fail-open on purpose, so a missed bind is silent; typed prompts reaching the hook in another form are not verified). Say so, show `<skill dir>/scripts/install-hooks.sh project-status --repo <repo_root>`, and offer: (a) with my yes, bind by hand `<skill dir>/scripts/session-map.sh bind <ID> --reason "bind hook did not fire" --session <id> --repo <repo_root>` (only adds protection, logged) and run this check again; (b) stop. **Only if soft mode is on and recorded** (`soft_mode: on` in the config) this check warns instead, notes "session not bound" in the ticket file and carries on in soft mode (stop point `local`, ask before every commit). If the first word differs from the real ID this is fixed at stage 1 (SKILL.md section 3b).
