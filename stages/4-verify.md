# Stage 4 - Verify (definition of done)

Done = **every in-scope AC has evidence** + the **common DoD** from config (lint/build/tests green, related flows not broken, no secrets in diff/logs/evidence, risk areas reviewed). Verify checks only against these - nothing extra. Gate by tier: A layers 1-2 (auto); B layers 1-3 (I look at the real app/API once); C layers 1-4 + extras, me.

## 0. Environment for the real run (only what this ticket needs; ask before starting anything long-running)
- Ports: each port the run needs is free, or owned by **this** worktree (`lsof -i :<port>` plus the process's cwd). A server from another worktree or the main checkout on that port = wrong server; stop and tell me, don't kill it.
- Start dev servers with this ticket's ports on the command line (`PORT=<n> <cmd>`; port block in the ticket file). Never edit `.env`.
- Env **key names** the run needs are present: `<skill dir>/scripts/env-keys.sh <file>` (names only); missing -> ask me to add; never print values.
- Model/provider config; signed-in browser state. A sign-in wall -> **I sign in**; you never type a password. Test identities: fake data only.

## 1. Automated (Claude)
lint, build, unit tests including new tests for changed logic; e2e if the project has it. All from the worktree. A failure -> triage below, then back to stage 3 (twice -> stop).
**Before you run anything, read `<state>/project.md` Commands and the `config.md` Verify notes.** Run lint, test and build **for every package or app the diff touches**, with its documented command (for a change under `apps/agent` in `copilot-kit-training`: `pnpm build:agent` and `pnpm --filter agent test`, not only `pnpm build`, which excludes the agent). A root command or a Turbo cache hit counts only for the packages it covers: say which. **Turbo (a repo with `turbo.json`):** every script that runs turbo (`pnpm lint`, `pnpm build`, ...) gets `--cache-dir=<this worktree>/.turbo/cache` (in `_base`: `<repo>/.claude/worktrees/_base/.turbo/cache`), e.g. `pnpm lint --cache-dir=<worktree>/.turbo/cache`. From a git worktree Turborepo otherwise puts its local cache into the **main** checkout's `.turbo/cache` (Turborepo docs, "Git Worktree Cache Sharing"): outside the sandbox's `allowWrite`, so the run fails with "Operation not permitted" (dry run DRY-01), and it would mix ticket outputs into the main checkout's cache. Never ask for `<repo>/.turbo` to be made writable. A documented command that is known to fail on the base (`project.md` / config say so) is not "build ok": run the pre-existing triage below, report the failure with the base commit, and never write that the build passed. **Push record:** when `guard.json verify.on_push` is not empty and the work is committed (clean worktree, untracked files included), run `<skill dir>/scripts/verify-record.sh <ID> --guard <state>/guard.json` last. It runs the `verify.on_push` commands itself, inside the sandbox (with a `turbo.json` in the worktree it sets `TURBO_CACHE_DIR=<worktree>/.turbo/cache` for them, so a plain `pnpm lint` there does not hit the main checkout's cache), and writes `<state>/evidence/<ID>/verify.json` (HEAD tree, exit code and command hash per key). The push hook no longer runs anything: it reads that record and blocks the push when it is missing, failed, or for another tree or command. Commit again after any code change, then record again. The record is tamper-evident, not tamper-proof. It covers only the `on_push` commands, so it is not a substitute for this layer.

### When a check fails: triage before touching code
1. **Is the failure caused by a stale fact?** A command, path, port or script name taken from `project.md` that does not exist or behaves differently (`command not found`, missing script, wrong port, file not found). If yes: verify the fact against its real source (`package.json`, config files, the code), fix that `project.md` section with the source, re-run the check **once**, note the mismatch in the stage report, and propose widening that section's `watch:` globs so `<skill dir>/scripts/project-map-stale.sh` would have caught it. If the wrong value is in `config.md` (a confirmed decision, for example a verify command) -> do **not** edit it; show me the evidence and ask.
2. **Pre-existing or regression?** Run the same command on the base, **never in the main checkout** (build and lint write `.next` / `dist` / `.turbo` there and can break a dev server I have running). Use the shared detached base worktree, each step its own Bash call (repo root and base branch from `guard.json`): (a) from the ticket worktree, `git merge-base HEAD <base_branch>` prints the base commit; (b) `<skill dir>/scripts/base-worktree.sh acquire <ID> <that sha> --repo <repo_root>`, with the sha written out literally - **no `$( )` and no backticks in a skill-script call**: the sandbox exclusion and the allow rule match the command text (lint). It runs outside the sandbox with the repo's git hooks off, refuses a commit that is not on `<base_branch>`, and prints `<repo>/.claude/worktrees/_base`, checked out detached at that commit; (c) `<skill dir>/scripts/setup-worktree.sh <repo_root> <repo_root>/.claude/worktrees/_base _base` links the env files and installs dependencies there, inside the sandbox (no port block for `_base`); if it fails, say so - a base check that then fails is not evidence of a pre-existing failure. Run the same command on `_base` **from the ticket session, without `cd`**: a ticket session is isolated in its worktree and Claude Code resets a `cd` out of it ("Shell cwd was reset"; in DRY-02 the first "base" run silently ran in the ticket worktree). Use the tool's directory option with absolute paths, e.g. `pnpm --dir <repo_root>/.claude/worktrees/_base <script> --cache-dir=<repo_root>/.claude/worktrees/_base/.turbo/cache` for a turbo script; a command without such an option -> stop and ask me. Save the output the stage-3 way (`... > <state>/evidence/<ID>/base-<check>.txt 2>&1; echo "exit $?"`, literal path; the exit code goes into the ticket file) and check that it names `_base` paths (pnpm prints `> <package> <script> <dir>`): no `_base` path -> it is not a base run, say so. Then `<skill dir>/scripts/base-worktree.sh release <ID> --repo <repo_root>`. Exit 3 (tracked changes in `_base`) or 4 (held by another ticket) -> stop and tell me; `git-safe: ...` (exit 2, arguments or git config refused) -> stop and show me the message, no retry in another form. `_base` is reused by every ticket and never removed by the skill: removal only with my OK (listed at cleanup). Compare the two outputs: `<skill dir>/scripts/compare-failures.py <base-output> <ticket-output> --root-base <dir> --root-ticket <dir>` (text heuristic; if the output format does not suit it, compare by hand and say which lines). Same failure on the base -> **pre-existing**: report it with the command and the base commit, do not fix it (CLAUDE.md "report pre-existing errors"), it is not a regression and does not block. A failure only on the ticket -> **regression**: fix it (stage 3). Never skip or loosen a check to get past either.

### Known sandbox limit: `next/font` Google Fonts (C11c4)
Signature in the output of a check run in the sandbox: `next/font: error:` with ``Failed to fetch `<font>` from Google Fonts``, or `There was an issue establishing a connection while requesting https://fonts.googleapis.com/`. Cause (C11c4, `docs/plan.md`): Turbopack checks the TLS certificate through the macOS trust service (trustd), which the sandbox blocks; allowing the font hosts does not help. Then:
1. Report the check as **"known sandbox limit: TLS check via trustd blocked (C11c4)"**. It is never "build ok".
2. Still run the base comparison (triage step 2) and report its result with the base commit.
3. Do not work around it: no `allowed_domains` / `dangerouslyDisableSandbox` parameter, no settings change asked for (`allowedDomains`, `enableWeakerNetworkIsolation`, `allowMachLookup`, `excludedCommands`), no change to the project's fonts unless an AC asks for it.
4. **Warn me first:** run in my terminal the command is **not sandboxed** and executes the ticket's code and package scripts (`next.config.*`, `postinstall`, plugins). Show `git diff --stat <base>...HEAD` (base commit from triage step 2) and ask me to review the diff before I run anything. Only then ask me to run the same command myself, in my own terminal, in the ticket worktree: give me the worktree path, the exact command (with the same `--cache-dir`) followed by `; echo "exit=$?"`, and the HEAD commit (`git rev-parse HEAD` as its own call, worktree clean). I paste the output.
5. Save my paste verbatim to `evidence/<ID>/user-run-<check>.txt`, first line `user-run: <command> | worktree <path> | HEAD <sha> | <date>`. In the stage report and the AC table the check's result is that output, marked **user-run** (not run by Claude). No paste, no `exit=` line, or HEAD changed since -> the check stays **unverified**.
6. If the command is in `guard.json verify.on_push`: `verify-record.sh` runs it in the sandbox and records the failure, so the push hook blocks the push. A user-run paste never updates `verify.json` (Claude could write that file itself). Tell me that I push myself; do not try to get around it.

## 2. AC -> evidence table (Claude drafts, I review) - `templates/ac-evidence.md`
One row per AC: the **pass criterion copied verbatim from the AC** (never paraphrased), how verified (test name / manual step), result, evidence link (`evidence/<ID>/...` in the state dir). **Read the criterion strictly**: `pass` only if the observed outcome satisfies it as written. For an either/or criterion (for example "exactly that item is moved, or the assistant asks which one") say which branch happened; an outcome that is neither branch (for example one item moved after an ambiguous name, with no question asked) is `fail`. A criterion that is ambiguous is `unverified` plus a question for the decision-maker, never read in favour of pass. Unverified ACs are marked **unverified**, never pass; waiting ACs **waiting**. Type the gaps: **missing** / **partial** / **contradicts**, plus **unrequested** (diff changes no AC asks for: justify or remove). "Done" in a task list or a commit message is not evidence.

## 3. Real run (tier B and C)
Happy path once + the designed edge cases, by project type (config `Type`):
| Type | Real run | Evidence |
|---|---|---|
| Web FE | browser (Playwright MCP / browser pane) or a Playwright test | screenshot, network request, console |
| BE / API | call endpoints (`curl` / HTTP client) | request + response, status, logs |
| Job / worker | run with sample data | logs, DB state before/after |
| CLI / library | run the command / example | output |
| Mobile | simulator | screenshot |
Driving a browser is exploratory evidence (not repeatable, costs tokens); writing a Playwright test is repeatable. Prefer state checks over full-page snapshots. Stop after one repro of a bug that blocks every case. Evidence stays in the state dir; it may hold client or personal data - not attached to the MR without checking.

## 4. Regression (tier C; B if config says)
Flows near the change still work; scope from config `regression scope` (`<ASK>` -> ask me).

## Tier C extras
Error/edge cases; a **fresh-context AC check**: a subagent gets only the AC table, the evidence and the diff (not this conversation) and confirms each AC has real evidence (`templates/reviewer-verify.md`); short result back. AI-agent flows are run 3 times with state assertions. An exploratory run.

## Client-side cache of per-user data
If the project has user accounts and caches per-user data on the client (browser/device storage, persisted store): DoD item - on sign-out or user switch the cache is cleared or kept per user.
